## Executive summary — read this first

The single most important fact in this repo is this: **the exact capability Step 4 scores — live cross-referencing of detections against a watchlist DB with real-time alert generation — does not exist in the running code.** Vehicle *detection* (YOLO26m, fine-tuned) is real. Everything downstream of it — plate reading, watchlist matching, alert creation, and cross-camera route reconstruction — is a stub that fabricates plausible-looking output:

- `pipeline/plate/interface.py`'s `PlateRecognizerStub` doesn't read the plate in the frame. It hashes the bounding-box coordinates and deterministically generates a well-formed but fictitious plate string (`GJ-01-AB-1234`-style). `pipeline/detection/writer.py` — the code that writes every row of the `detections` table — defaults to this stub (`self.plate_recognizer = plate_recognizer or PlateRecognizerStub()`). There is no code anywhere in the repo that calls PaddleOCR, EasyOCR, or any OCR engine; `pipeline/ocr/__init__.py` is a one-line empty package literally named "future work."
- No code path anywhere in `model2_analytics/app` or `model2_analytics/pipeline` ever inserts a row into the `alerts` table. The only `INSERT INTO alerts` in the entire repo is in `shared/db/seed.sql` — canned demo data. `pipeline/events/__init__.py`, the module that would own this logic, is an empty "future work" stub. The `/watchlist` router only does CRUD on watchlist *entries themselves* (add/edit/delete a wanted plate) and cascade-deletes alerts when a watchlist entry is removed — it never creates one from a live detection.
- Cross-camera tracking (`vehicle_track_id`, the thing that makes "trace the vehicle across the network" possible) is generated by `TrackAssociatorStub` in `pipeline/tracking/associator_interface.py`, described in its own docstring as returning "a consistent global vehicle_track_id based on plate/feature seed" — i.e. derived from the same fabricated plate, not from any real re-identification. `pipeline/reid/__init__.py` is empty, also marked "future work."
- The person-watchlist face-matching side has the same shape: registering a person with a photo and generating a 512-d embedding is real and reasonably sophisticated (5-gate quality check, YuNet + solvePnP pose, InceptionResnetV1, pgvector/HNSW storage). But nothing in the codebase ever *runs* that matching against a live or recorded feed — there's no code that pulls a face out of a video frame, embeds it, and queries the watchlist. `faceembedding/encoder.py` also carries `# TODO: Calibrate against validation set; placeholder only` next to its similarity threshold, meaning even if matching were wired up, the accept/reject threshold is an unvalidated guess.

None of this is disclosed anywhere — not in `README.md`, not in `model2_analytics/README.md`, not in `docs/API_Contract.md`, not in `Project_Context.md`. Every one of those documents describes watchlist matching and alerting in the present tense as something the platform does. A judge who reads the docs, then opens `/detections` or the output report and sees a plausible plate number and a "MATCH" badge, is being shown something that looks like Step 4's scored capability and isn't it. That is a materially different risk than "this feature is unfinished" — it's the gap between "unfinished" and "looks finished." `HackathonPortal.md` Step 3 says explicitly: *"Mock-ups, animations, simulated interfaces, or concept videos without an operational backend will not be considered."* The plate/watchlist/alert path as it stands today is exactly that pattern sitting behind a backend that is operational for everything else, which makes it more dangerous, not less — it will pass a casual look and fail the moment a judge tests it with a real plate, or asks "walk me through the match logic," or feeds the government camera a car that shouldn't match anything and watches it match anyway.

**This is not a documentation problem and screenshots will not fix it.** It is the load-bearing wall of the whole submission: Step 4 (the scored test case), the PPT's "methodology for correlating live CCTV feeds with watchlist databases," and the HLD's alert-generation workflow all assume this exists. Everything else in this report — including the real documentation gaps — is secondary until this is either (a) genuinely implemented at least for the plate path, even crudely (a real OCR call, even unfine-tuned EasyOCR, beats a hash function), or (b) explicitly and visibly reframed in every deliverable as a stubbed interface with a credible integration point, the same honest-disclosure pattern `Project_Context.md` §6 already uses for at-rest encryption and network segmentation. Given the timeline, (b) is the realistic move for alerts/re-id, but (a) is very likely achievable for plate OCR alone — EasyOCR/PaddleOCR are drop-in against the existing `PlateRecognizerInterface`, and the interface was clearly designed for exactly this swap (see "What's already solid" below).

## 1. Critical findings — detail

### 1.1–1.3: the fabricated plate → track → alert chain

Already walked through in the executive summary with file-level evidence. One more detail worth surfacing for whoever fixes this: the interface design is genuinely good — `PlateRecognizerInterface` and `TrackAssociatorInterface` are clean abstract base classes with a documented contract ("Future OCR engines implement this and swap in... without modifying the database writer or downstream pipeline"). This was clearly built with the swap in mind, which means the fix is a real implementation behind an interface that already exists, not an architecture change. That changes the cost-benefit here a lot: this isn't "redesign the pipeline in the time remaining," it's "write one class."

Concretely, for the plate path: `pip install easyocr` (or PaddleOCR), implement `EasyOCRRecognizer(PlateRecognizerInterface)` in `pipeline/plate/`, crop to `vehicle_bbox`, run it, return a real `PlateResult`. It will be slower and less accurate than a fine-tuned model, and that's fine — Project_Context.md §5 exists specifically so an honest, measured, imperfect number is the expected output, not a claimed 99%. A real OCR read at 60% exact-match rate with a measured confusion matrix is categorically stronger material for the PPT and for surviving a live judge test than a fake 100% match rate that collapses under one real question.

For alerts: the schema (`alerts`, `detections.vehicle_track_id`, `alerts.acknowledged_by/acknowledged_at`) is already fully designed per `Project_Context.md` §4 and §6 — the write path is what's missing. A single function that runs on each `on_detection_event()` call in `detections.py` — normalize the plate, query `vehicles_watchlist`, insert an `alerts` row on match, push over the existing WebSocket hub — is a small, well-scoped piece of work sitting on infrastructure (WS hub, DB session, detection event pipe) that already exists and already works.

For cross-camera tracking specifically: given the timeline, Project_Context.md §4's own fallback design (join by plate string + timestamp as primary, appearance-based re-id only as a fallback for OCR misses) means you don't need real re-id to satisfy Step 4's "trace the vehicle across the network" if the plate join is real — that alone gets you a genuine multi-camera route reconstruction query against `vehicle_track_id`/`detections`, which is most of what the scored test needs. Re-id becomes a stretch item, not a blocker, once plate OCR is real. That reordering — fix OCR first, treat re-id as bonus — is probably the single highest-leverage sequencing decision available right now.

### 1.4: person-watchlist matching never runs

Registration is solid engineering (quality gates, pose correction, real embedding model, vector index) — this is not a criticism of that code. But as it stands, a judge cannot demonstrate "correlate a face against the watchlist and get an alert" at all, for any input, because no endpoint or worker ever extracts a face from a frame and queries `persons_watchlist` by embedding similarity. Given face recognition was explicitly "bonus/stretch, cut unless everything else is done early" per `Project_Context.md` §4, and it clearly got built anyway (per AuditReport2.md's own note), the registration half is sunk cost worth keeping — but budget real time to decide whether the *matching* half is worth finishing given findings 1–3 are the ones Step 4 actually scores. If time runs out, the honest move is to present person-watchlist as "registration and embedding pipeline complete, live matching not yet wired up" rather than implying it works end-to-end.

### 1.5: undisclosed gap across every document

This is the one that turns "unfinished feature" into "submission integrity risk." `docs/API_Contract.md`, `README.md`, and `model2_analytics/README.md` all describe ANPR, watchlist matching, and alerts as present-tense platform capabilities with no caveat. Compare this to how `Project_Context.md` §6 already handles the at-rest-encryption gap — a plain, explicit "what we document but don't build" list. That's the right pattern and it already exists in this repo's own culture; it just hasn't been applied to the plate/alert/re-id stubs yet, probably because they were built later than that section was written. Fixing the disclosure costs almost nothing (it's a paragraph in three files) and it's the difference between a judge reading "known limitation, here's the real interface and integration point" (credible, still scores well on architecture) versus a judge discovering an unlabeled fake mid-demo (much worse than the same gap disclosed up front — this exact risk is what `HackathonPortal.md` Step 3's mock-up warning is protecting against).
